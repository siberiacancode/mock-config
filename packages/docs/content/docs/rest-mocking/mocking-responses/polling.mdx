---
title: Polling
description: Simulate polling behavior with queue-based cycling responses in Mock Config.
---

Some APIs are polled repeatedly by the client — a job status endpoint, a progress tracker, a notification feed. Mock Config supports this pattern with a **queue**: an ordered list of responses that the server cycles through as requests come in.

```ts
import { rest } from 'mock-config-server';

rest.get('/job/status', {
  queue: [
    { response: { status: 'pending' }, time: 3000 },
    { response: { status: 'processing' }, time: 3000 },
    { response: { status: 'done' } }
  ]
});
```

## Queue Items

Each item in a queue has a `response` (or `handler`) and an optional `time` field.

| Field      | Type     | Description                                                         |
| ---------- | -------- | ------------------------------------------------------------------- |
| `response` | `any`    | Static response returned while this item is active.                 |
| `handler`  | function | Dynamic resolver called while this item is active.                  |
| `time`     | `number` | How long, in milliseconds, this item stays active before advancing. |

## Time-Based Items

When an item has a `time` value, it stays active for that many milliseconds. Every request that arrives during that window receives the same response. After the time elapses, the queue advances to the next item.

```ts
rest.get('/job/status', {
  queue: [
    { response: { status: 'pending' }, time: 3000 },
    { response: { status: 'processing' }, time: 3000 },
    { response: { status: 'done' } }
  ]
});

// GET /job/status → { status: 'pending' }   (active for 3 s)
// GET /job/status → { status: 'pending' }   (still in the 3 s window)
// GET /job/status → { status: 'processing' } (active for 3 s)
// GET /job/status → { status: 'done' }       (no time → advances on next request)
// GET /job/status → { status: 'pending' }    (queue looped)
```

Here the first two items each hold for 3 seconds. The third item has no `time`, so the queue advances on the next request after it becomes active.

## Request-Based Items

When an item has no `time`, it advances immediately after the first request that hits it. Each subsequent request moves to the next item.

```ts
rest.get('/notifications', {
  queue: [
    { response: [] },
    { response: [{ id: 1, text: 'New message' }] },
    {
      response: [
        { id: 1, text: 'New message' },
        { id: 2, text: 'Another' }
      ]
    }
  ]
});

// GET /notifications → []
// GET /notifications → [{ id: 1, text: 'New message' }]
// GET /notifications → [{ id: 1, text: 'New message' }, { id: 2, text: 'Another' }]
// GET /notifications → []  (queue looped)
```

## Queue Loop

When the last item is reached, the queue loops back to the first item. The polling client will continuously cycle through the defined states.

## Matching With Polling

You can combine a queue with a matcher to scope it to specific request conditions.

```ts
rest.get('/status', {
  match: { headers: { 'x-session': 'abc' } },
  queue: [
    { response: { progress: 0 }, time: 1000 },
    { response: { progress: 50 }, time: 1000 },
    { response: { progress: 100 } }
  ]
});
```

Only requests with the matching `x-session` header participate in this queue. Other requests fall through to the next matching route.

## Dynamic Queue Items

A queue item can use a `handler` function instead of a static `response` when the reply depends on the request.

```ts
rest.get('/data', {
  queue: [
    { handler: ({ request }) => ({ id: request.params.id, status: 'loading' }), time: 2000 },
    { response: { status: 'done' } }
  ]
});
```
